# VaiBReport — Home redesign + catalog-wide `compare_to` editorial layer

**Status:** spec
**Date:** 2026-05-01
**Author:** Peter Wheeler (with Claude)
**Related:** `docs/LLM-CASCADE.md`, `.management/api-costs.md`, `.github/workflows/generate-digest.yml`

---

## Problem

The VaiBReport homepage is the only page most visitors reach. It currently surfaces 10 dated digest titles in a flat text list — no thumbnails, no previews, no editorial highlights. Beyond the homepage, individual `repo.html`, `tool.html`, and `research.html` pages render unique editorial content that visitors never discover because the discovery layer (homepage → catalog → detail page) is functionally text-only and dense.

Two compounding effects:
1. **Cramped homepage** — typography is small (14px, 1.7 line-height), spacing tight, no visual surfaces to anchor the eye.
2. **No editorial differentiation per repo** — the catalog is 963 items deep, but each repo page shows the same shape (description, stats, link). There's no signal of *what makes this item interesting relative to the alternatives*.

## Goal

Redesign the homepage to lead with visually rich, editorially-weighted hero cards, *and* introduce a catalog-wide editorial layer (`replaces` + `similar_to`) so every individual repo page in the catalog inherits the same editorial weight as the homepage heroes.

The editorial layer is generated by the existing NIM-tier LLM cascade (free), validated adversarially by a different-family NIM model before write, and supplemented by a manual override file for cases where the LLM is wrong.

## Non-goals

- No rebrand. The cyberpunk aesthetic, terminal typography, source-color accents, scanline overlay, and component library all stay.
- No new platforms or fetchers. Data sources are unchanged.
- No new auth or user accounts.
- No replacement of the existing daily digest pipeline — this extends it.
- No automated visual regression testing. Manual smoke + Stitch exploration is sufficient at this site's scale.

---

## Approach

**Approach 3 — two parallel tracks coupled by a small schema contract:**

1. **Schema contract** locked first (front-matter shape for new fields). Both tracks build against this.
2. **Track A (pipeline):** extend the existing LLM cascade in `generate-digest.yml` to produce `replaces` + `similar_to` per item. Add an adversarial cross-family validator pass. Build a one-shot backfill script for the existing 963 catalog items. Wire daily digest runs to write the new fields going forward.
3. **Track B (design + UI):** loosen typography tokens at `default.html` level, build new `.hero-card` component, redesign `home.html` to surface today's heroes, update `repo.html` to render the editorial chips, extend `repos.md` catalog filters with a `Replaces` dimension. Stitch handles visual exploration of the hero-card variants.
4. **Feature flag** (`JEKYLL_ENV=compare_to_live`) gates the UI changes so either track can ship independently.
5. **Override file** (`config/compare-to-overrides.json`) is the manual safety net for cases the validator wrongly drops or the generator misses.

## Schema contract

Every `_repos/<slug>.md` gets two new front-matter fields plus two metadata fields:

```yaml
replaces:
  - name: "Notion"
    url: "https://www.notion.so"
    note: "knowledge base + docs"   # optional, ≤60 chars
  - name: "Airtable"
    url: "https://airtable.com"
    note: "lightweight DB"
similar_to:
  - "calcom--calcom"                # must match an existing _repos/<slug>.md
  - "agent-browser"
compare_to_source: "llm"            # "llm" | "override" | "manual"
compare_to_validated: true          # validator approved
```

**Rules:**
- `replaces`: max 5 entries, min 0. Empty `[]` is valid and common.
- `similar_to`: max 4 entries, min 0. Every slug must match an actual `_repos/*.md` filename; unknown slugs are dropped silently at write time.
- `compare_to_source`: provenance — `"llm"` (generated), `"override"` (from overrides file), `"manual"` (hand-edited in front-matter).
- `compare_to_validated`: `true` only after the cross-family validator approves. UI hides unvalidated entries.

**LLM cascade JSON output (extension of existing blurb format):**

```json
{
  "owner/repo": {
    "blurb": "One-line editorial blurb.",
    "replaces": [
      {"name": "Notion", "url": "https://www.notion.so", "note": "knowledge base + docs"}
    ],
    "similar_to": ["calcom--calcom", "agent-browser"]
  }
}
```

**Override file shape (`config/compare-to-overrides.json`):**

```json
{
  "agent-browser": {
    "replaces": [
      {"name": "Browser Use", "url": "https://browser-use.com"},
      {"name": "Multi-On", "url": "https://multion.ai"}
    ],
    "similar_to": ["lavague-ai--lavague"],
    "compare_to_source": "manual"
  }
}
```

Per-field override: missing keys preserve the LLM output for that field. Allows partial overrides (e.g., override `replaces` only, keep LLM `similar_to`).

## Track A — pipeline architecture

### A.1 Cascade prompt extension

`generateEditorialBlurbs()` in `.github/workflows/generate-digest.yml` builds one big prompt and parses one JSON map. Extension:

- Prompt asks for three nested fields per item (`blurb`, `replaces`, `similar_to`) instead of one bare string.
- Prompt includes explicit hallucination guard: *"If you do not know real commercial products this replaces, return `replaces: []`. Do not invent product names."*
- Parser walks the new nested shape; existing failover loop in `tryCascadeBlurb()` is unchanged.

### A.2 Adversarial validator

New function `validateCompareTo(generated, generatorModelName)` runs after cascade returns:

1. **Cross-family pairing** — picks a NIM model from a different lineage than the generator:
   - Generator Llama family (`meta/llama-3.3-70b-instruct`, `meta/llama-3.1-405b-instruct`) → validator Mixtral or Qwen.
   - Generator Mixtral → validator Nemotron or Qwen.
   - Generator Qwen → validator Llama or Mixtral.
   - Generator Local Qwen → validator Mixtral or Llama on NIM.
   - Generator Gemini/OpenRouter/Groq/Haiku → validator any NIM model.
2. **Adversarial prompt** — explicitly instructs the validator to find what's wrong, not to confirm correctness:
   > *"For each item below, find what's wrong with the generated `replaces` and `similar_to` lists. Drop entries where the commercial product doesn't exist or the displacement claim is implausible. Drop `similar_to` slugs that aren't functionally similar. Return JSON `{slug: {keep_replaces: [indexes], keep_similar_to: [indexes], reasons: {dropped_index: 'short reason'}}}`."*
3. **Merge** — only entries the validator kept survive. Survivors get `compare_to_validated: true`.
4. **Disputes log** — drops with reasons go to `data/compare-to-disputes-YYYY-MM-DD.json` for spot-checking. Debug artifact, not committed long-term.
5. **Validator failure mode** — call fails / parse fails / rate limit → all generator output ships with `compare_to_validated: false`. Degraded mode, never blocks the digest.

### A.3 One-shot backfill script

`scripts/backfill-compare-to.js` (new file):

- Walks `_repos/*.md`, parses existing front-matter.
- Skips items already populated (idempotent re-runs).
- Batches remaining items 15-per-prompt.
- Calls the same `tryCascadeBlurb` + `validateCompareTo` pipeline as the digest workflow.
- Validates `similar_to` slugs against actual `_repos/*.md` filenames; drops unknowns.
- Merges `config/compare-to-overrides.json` per-field.
- Writes new front-matter back to each file.
- Commits in batches of 50 with messages like `backfill: compare-to fields, items 51-100`.
- Logs progress to `data/backfill-compare-to.log` for resumability.

**Run modes:**
- `node scripts/backfill-compare-to.js --limit 50` — staged spot-check (first 50).
- `node scripts/backfill-compare-to.js --resume` — continues from last logged checkpoint.
- `node scripts/backfill-compare-to.js --dry-run` — prints planned writes, makes no changes.

### A.4 Daily digest integration

`generate-digest.yml` changes:
1. After cascade returns, call `validateCompareTo(generated, modelUsed)`.
2. `createRepoEntry()` includes `replaces` / `similar_to` / `compare_to_source` / `compare_to_validated` in the YAML front-matter when writing `_repos/<slug>.md`.
3. `data/health-YYYY-MM-DD.json` extended with `compare_to_generated`, `compare_to_validated`, `compare_to_disputed_pct` counters.

Digest post body (`_posts/YYYY-MM-DD-github-digest.md`) is unchanged. The new editorial fields surface only on `_repos/<slug>.md`, the homepage hero cards, and the catalog filter.

## Track B — UI architecture

### B.1 Typography & spacing tokens (`_layouts/default.html`)

Loosen at the `:root` level so every page benefits:
- `body` font-size 14 → 15.5px, line-height 1.7 → 1.8
- `.page-content` max-width 1100 → 1180px, padding 2rem → 2.75rem desktop, 1.25 → 1.75rem mobile
- `.prose p` line-height 1.75 → 1.85, paragraph margin-bottom 1rem → 1.25rem
- New `--gap-loose: 1.5rem` and `--gap-tight: 0.75rem` tokens; replace ad-hoc gap values across layouts

All existing components, colors, and the cyberpunk identity are preserved.

### B.2 New `.hero-card` component

**CSS** lives in `_layouts/default.html` shared styles (alongside `.archive-card`, `.entry-card`, etc. — it's a reusable component).
**Liquid template** lives in `_includes/hero-card.html` — `home.html` renders one per featured item via `{% include hero-card.html item=... %}`.

Grid: 280px thumbnail column + flexible body. Body contains source-color top stripe, title in `--font-disp`, blurb, two stacked chip strips (`replaces`, `similar_to`), source badge bottom-right. Hover lifts 2px (matches `.archive-card`). Mobile: stacks single-column with thumbnail on top.

### B.3 `home.html` redesign

- Pulls today's digest post, parses out the first 5 featured items in document order (sections render in priority order already: SaaS starters → AI/LLM infra → Ops → Marketing → UGC → Trending oddballs → platform sections; the first 5 across that flat sequence are the heroes).
- Each hero is rendered via the `_includes/hero-card.html` template fed from the corresponding `_repos/<slug>.md` front-matter (which has the `replaces` / `similar_to` data plus `og_image`, source, blurb).
- Status row above the heroes: terminal-prompt-styled one-liner, *"YYYY-MM-DD · N picks across N sources"*.
- Recent-digests panel moves below the fold with reduced visual weight.

### B.4 `repo.html` updates

Two new sections render after `.repo-stats` block (only when data is present and `compare_to_validated == true`):
- **Replaces** — renders `replaces[]` as link chips with optional `note`.
- **Similar in catalog** — renders `similar_to[]` as internal links to `/repos/<slug>/`.

Hidden gracefully when empty.

### B.5 `repos.md` catalog filter extension

One new chip row: *"Replaces:"* with chips for the **12 most-frequent `replaces[].name` values** across all `_repos/*.md` entries. Computed at Jekyll build time via Liquid aggregation, baked into the page's existing `repoData` JS array as a `replaces` field per item. Clicking a chip filters to items where any `replaces[].name` matches. Filter logic added to existing JS (~30 lines).

### B.6 Stitch role

Stitch generates the visual exploration of `.hero-card` variants:
- Three layouts (thumbnail-left, thumbnail-top, thumbnail-bleed-edge).
- Three intensity levels for the chip-strip treatment.

We pick one, hand-translate the winning Stitch design into the existing `--ink/--bg/--font-mono` token system. Stitch is exploration only — its raw HTML/CSS does not ship.

### B.7 Feature flag

Single env var read at Jekyll build time: `JEKYLL_ENV=compare_to_live`. When set, `home.html` renders heroes + chips and `repo.html` renders the new sections. When unset, both render the existing pre-redesign UI. Lets either track ship independently and supports local A/B preview.

## Data flow

```
Daily fetchers (unchanged) → data/<source>-YYYY-MM-DD.json
        ↓
generate-digest.yml runs at 14:00 UTC
        ↓
loadLatestDataFile() per source → candidates filtered by cooldown/seen
        ↓
generateEditorialBlurbs(candidates, sections)   [prompt extended for replaces/similar_to]
        ↓
tryCascadeBlurb(prompt)   [unchanged failover; returns winning model name]
        ↓
validateCompareTo(generated, generatorModelName)   [NEW: cross-family NIM validator]
        ↓                                       ↓
   keeps + drops                  data/compare-to-disputes-YYYY-MM-DD.json (debug)
        ↓
mergeOverrides(merged, config/compare-to-overrides.json)   [per-field override wins]
        ↓
validateSlugs(merged)   [drops similar_to slugs that don't match _repos/*.md]
        ↓
createRepoEntry() writes _repos/<slug>.md with new front-matter fields
        ↓
_posts/YYYY-MM-DD-github-digest.md written (body unchanged)
        ↓
data/health-YYYY-MM-DD.json includes compare_to counters
        ↓
git commit + push   [unchanged retry-pull-rebase loop]
        ↓
deploy-blog.yml builds Jekyll site:
  - home.html reads today's digest, renders hero cards
  - repo.html renders new chip sections when compare_to_validated
  - repos.md exposes Replaces filter
```

The backfill script (`scripts/backfill-compare-to.js`) hooks the same middle pipeline (cascade → validator → override-merge → slug-validate → write), iterating over existing `_repos/*.md` instead of new digest candidates.

## Error handling

| Failure | Handling |
|---|---|
| Generator cascade exhausted (every model fails) | Existing template fallback — blurbs become repo descriptions, `replaces`/`similar_to` set to `[]`, `compare_to_source: "manual"`, `compare_to_validated: false`. Digest still ships. |
| Validator call fails (rate limit, parse error) | All generator output ships with `compare_to_validated: false`. UI hides unvalidated entries. Logs warning, never blocks. |
| Validator returns invalid JSON | Same as call failure — degrade to unvalidated. No JSON-repair attempt. |
| `similar_to` slug doesn't match any `_repos/*.md` | Dropped silently at write time. No log entry — these are common as the catalog evolves. |
| Override file has malformed JSON | Workflow logs warning, proceeds without overrides. |
| Override file references a slug that doesn't exist | Override entry ignored. Logged once per run. |
| Backfill script interrupted | `data/backfill-compare-to.log` records last-completed batch. `--resume` picks up. |
| Backfill running while daily digest workflow fires (concurrent writes to `_repos/<slug>.md`) | Backfill checks `git status` before starting each batch; if the working tree is dirty or a `digest-running.lock` file exists in `data/`, pauses 60s and retries. Daily workflow creates/removes the lock file as its first/last step. Prevents merge conflicts on long backfill runs. |
| Validator hallucinates a "drop" reason for a clearly-correct entry | Recall-loss tradeoff already accepted. Override file is the human safety net. |
| LLM emits a fake commercial product the validator misses | Spot-check gate at backfill stage 1 (50 items) catches systemic cases. Ongoing daily leakage accepted; override file handles individual cases. |
| UI bug crashes new home rendering | Unset `JEKYLL_ENV=compare_to_live`. Single env-var rollback. |

## Testing

### Pipeline (Track A)
- **Spot-check gate:** backfill `--limit 50` first; manually eyeball 10 random `_repos/*.md` outputs. Manual gate, not automated.
- **Slug validation unit test:** fake `_repos/` directory, confirm `validateSlugs()` drops unknowns. ~15 lines.
- **Override merge unit test:** confirms per-field override (override `replaces` only, LLM `similar_to` survives). ~20 lines.
- **Validator pairing unit test:** generator-Llama → validator-not-Llama, etc. Pure function.
- **Health-check counters:** `data/health-YYYY-MM-DD.json` extended with `compare_to_generated`, `compare_to_validated`, `compare_to_disputed_pct`. Anomaly = drop in validation rate.

### UI (Track B)
- **Jekyll build validation:** existing `jekyll-build-validator` agent in `.claude/agents/`. Run after every layout change.
- **Manual smoke test:** `bundle exec jekyll serve`, hit `/`, `/repos/`, `/repos/<real-slug>/`, `/picks/`, `/leaderboard/`. Confirm: heroes render, chips render, no console errors, theme toggle works, mobile breakpoint stacks correctly.
- **Visual regression:** opt-out. Stitch exploration + manual eyeballing sufficient at this site's scale.

### Cross-track integration
- **End-to-end test:** run backfill on 3 hand-picked items, confirm front-matter writes, confirm `home.html` renders them as heroes if they're in today's digest, confirm `repo.html` renders chips. Manual.
